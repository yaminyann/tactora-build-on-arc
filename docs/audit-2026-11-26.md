# Full audit, 2026-11-26

Scope: every part of the repository at commit `acf4df1` (branch `phase-3-contract-v2`, working tree clean). Read-only: no source file was changed by this audit. Everything below was either read in the code or run; where something could not be checked it says so.

## 1. What the product is

Lumarc (repository name Arc Terminal) is a non-custodial trading terminal for Arc, Circle's USDC-gas chain.

| Part | What it does | Where |
| --- | --- | --- |
| Market swaps | The browser asks the backend gateway for quotes from KyberSwap and 0x (mainnet) or a test router (testnet), ranks them by guaranteed output after gas, and the user's wallet sends the aggregator's calldata. | `server/gateway/`, `src/components/MarketForm.tsx`, `src/trading/aggregator.ts` |
| Conditional orders and DCA | `ArcTradeOrders` escrows USDC or the token and lets any keeper execute when an oracle condition holds. Six order types (limit, stop-loss, take-profit, stop-limit, trailing stop, OCO) plus DCA. | `contracts/ArcTradeOrders.sol`, `src/components/ConditionalForm.tsx`, `DcaForm.tsx` |
| Keeper | Optional built-in bot that watches open orders, gets quotes, simulates, and sends `execute` or `executeMany`. Standby role, sharding, profit gate. | `server/keeper.ts`, `keeper-core.ts` |
| Indexer | Reads contract events into SQLite or Postgres for history, the admin log and market-swap reports. | `server/indexer/` |
| Agent Station | Chat in plain words or typed commands. Everything becomes one command of a fixed grammar, read back with exact numbers, confirmed, then signed by the wallet. Optional language model behind `POST /agent-chat`. | `src/trading/agent/`, `src/components/AgentStation.tsx`, `server/agent-chat.ts` |
| Pages | Home (landing), Trade, Dashboard, Agent, Settings, Admin (owner only). Hash routes. A connected wallet skips the landing page. Phones get a bottom tab bar. | `src/App.tsx`, `src/components/` |
| Deployment | `Dockerfile` (targets `web` and `api`), `docker-compose.yml`, nginx, Coolify scripts. | `Dockerfile`, `docker-compose.yml`, `deploy/`, `scripts/coolify/` |

Data flow: browser reads chain state straight from the public Arc RPC (wagmi/viem, multicall), reads quotes and token lists from `/api`, and sends every transaction through the user's injected wallet. The backend holds only the keeper key (optional). There is no user database.

Git state: `main` on origin is `910a88c` (PR #1 merged, 2026-11-13). The branch holds five more local commits (landing redesign, 2026-11-16) that are not pushed. Local `main` is stale at `cb6d5df`, which is the commit Coolify reported deploying.

## 3. Findings

Severity: High means do first (money, trust or blocked release). Medium means real defects or risks. Low is cleanup.

### High

**1. The landing page shows invented data and false safety claims.** `src/components/Landing.tsx`
- Lines 341 to 346 hard-code prices and 24h changes (`cirBTC/USDC 91,420.50 +3.12%`, `ARC/USDC 1.45 +6.20%`), line 412 labels the panel `LIVE L1`, line 416 says `Oracle Source: Chainlink Arc`, and lines 421 to 460 draw a fake order-book ladder. None of it is read from anything. There is no tradable ARC token.
- Line 569 says conditional orders "live in audited smart contracts". The contract is unaudited (`AGENTS.md`, `docs/security.md`, and the Terms text).
- Line 686 says `Audit State: Verified Open Execution`. Line 324 says `Custody Risk 0.00%`. Funds sit in an unaudited escrow contract, so the risk is not zero.
- Line 183 says "decentralized keeper network". There is one operator keeper; anyone can run another, but none is promised.
- Lines 48 to 57 present Circle, 0x, KyberSwap and Chainlink as a partner strip. No partnership exists. Lines 646 and 684 mention a "TypeScript SDK" and functions `executeOrder` and `dcaPlan` that do not exist (the contract has `execute` and `createDca`).
- Lines 303 and 311 state block finality and gas facts that nothing in the repo verifies.
- Why it matters: this is a finance product. Fabricated numbers and an audit claim are the kind of thing that causes real harm and legal exposure. It also breaks the project's own rule (`DESIGN.md`: every number real or labelled illustrative).

**2. Browser swap calldata is trusted beyond what the frontend verifies.** `src/trading/aggregator.ts:83-97`, `src/components/MarketForm.tsx:60-62`, `src/trading/agent/engine.ts:165-173`
- The calldata and target come from `/api/quote`. The frontend checks the target is on an allowlist and that value is zero. It does not check recipient, minimum output or amount inside the calldata. A compromised backend, or anyone able to alter `/api` traffic, could return calldata that sends the output elsewhere or accepts a very low minimum.
- Damage is capped because approvals are exact amounts, so at most the swap amount is at risk, but that is still the user's funds.
- The agent adds a 0.5% price-moved check, but it compares two numbers that both come from the backend.
- Fix direction: before the wallet prompt, simulate the transaction against the RPC and require the taker's balance change to meet `minBuyAmount`, or decode the Kyber and 0x calldata and verify recipient and minimum.

**3. Deployment build is not reliable.** Details and hypotheses in section 5.

**4. The public RPC is the bottleneck for every part of the system.**
- `src/config.ts` gives the browser one URL (`rpc.testnet.arc.io`), no fallback and no way to override it from the environment. The keeper ticks every 5 s and reads 4 or more values each time; the indexer polls every 5 s; the browser adds more.
- Measured: 18 separate `eth_call` HTTP requests in 30 s on an idle Trade page, about 36 per minute per open tab (polls: balances 12 s, orders 8 s, DCA 8 s, each oracle 15 s, execution logs 20 s).
- Seen during this audit: the test wallet bridge crashed on `eth_getBalance` with "rate limit exceeded", the market swap send failed with "Request exceeds defined limit", and an earlier session showed a browser CORS error from the same host (a throttled response without CORS headers). Real users on shared IPs will hit this quickly.
- Fix direction: `VITE_RPC_URL_*` with a fallback transport, a dedicated RPC for the server (`RPC_URL_Arc_Testnet` is already supported), batch the keeper's per-tick reads into one multicall, and reduce poll rates when the tab is hidden.

### Medium

**5. CI is red on `HEAD`.** `ci.yml` job `app` runs `oxlint --type-aware src scripts` and `oxlint .`. `Landing.tsx` has `no-explicit-any` (line 753), a floating promise (line 243), a mutation after render (line 91) and 22 unused imports and variables.

**6. Testnet price feeds are stale, so orders and DCA cannot be created on testnet.** The Trade page shows "The oracle price is stale." The harness feeds are registered with the longest allowed staleness (2 days) and only refresh when someone presses "Refresh feed". Nothing automates it. Related: `server/gateway/testrouter.ts:30-33` and `src/trading/aggregator.ts:194-198` turn every quote failure (stale feed, RPC rate limit) into `no_liquidity`, so users and the keeper see "No route has liquidity" for a different cause. During the audit the backend answered `no_liquidity` for a pair the browser could quote.

**7. Leftover Arc Studio code ships in the production bundle.** `src/main.tsx:1-2` imports `./tracing` (500 lines that wrap `fetch` and `window.ethereum.request`, enabled only by a parent-frame message in dev) and `./console-capture`; `src/config.ts:9` calls `registerChain`; `package.json` is named `studio-app`; `rpc.ts` and `.env.example` still describe the Studio RPC proxy; `src/onchain-*.ts` carry "Arc Studio writes this file" headers. The wrappers are inert in production but are pure risk and weight, and they contradict the earlier request to remove Studio traces.

**8. No Content-Security-Policy.** `deploy/security-headers.conf` sets only `nosniff`, a referrer policy and `X-Frame-Options`. For a wallet-connected app there should be a CSP (`script-src 'self'`, explicit `connect-src` for the RPC, Coinbase and `/api`), and HSTS if the proxy does not add it. Fonts load from Google at runtime.

**9. Agent protective actions hit the spend limit.** In the live test, "Protect your tBTC with an OCO" for about 90,091 USDC of holdings was refused: "above your per-command limit of 100 USDC". Stops, take-profits, OCO and cancels reduce risk but are counted against the same limits as buying. By default (100 per command) the suggestion feature cannot protect any real position.

**10. The landing animation ignores motion settings and costs CPU.** `Landing.tsx:76-190`: a canvas with 65 particles and an O(n squared) link loop runs forever, even with Settings > Motion off or `prefers-reduced-motion`. It hard-codes a green gradient, a grid and glow, which `DESIGN.md` forbids, and uses uppercase wide-tracked labels, pulsing dots and the invalid classes `py-0.2` and `bg-panel2`.

**11. Only an injected wallet connector.** `src/config.ts:22`. On a phone browser without a wallet extension nobody can connect, which undercuts the "mobile app" goal. WalletConnect needs a project id.

**12. Heavy, unused production dependencies.** Six `@circle-fin/*` packages are in `dependencies` but only `scripts/self-deploy.ts` and `scripts/compass-deploy.ts` import them. `bun install --production` in the `api` image installs all of them. See section 5.

### Low

13. Landing accessibility: `EcosystemAppsTable` rows are clickable `div`s with no keyboard access; the partner strip is clipped on anything under about 1200 px (items cut off, not scrollable); asset buttons are 26 px tall on phones; `navigator.clipboard.writeText` has no error handling.
14. `useOrders` and `useDcas` read every id in one multicall (`allowFailure: false`). The paged views in the contract are unused, so a heavy account makes one failing call fail the whole table.
15. The agent daily limit is in `localStorage`; clearing storage resets it. It is a convenience guard, not a security control, and should be described that way.
16. `POST /swaps` lets anyone insert any successful swap transaction hash into the history table. It re-derives everything from the chain, so it cannot write false data, but it can grow the table (rate limit is 30 per minute per client).
17. The keeper wallet holds 3.93 USDC; the low-balance alert threshold is 1 USDC.
18. `tests/` and `server/` fail `oxlint --type-aware` with about 100 findings (not part of CI today).
19. Documentation drift: `docs/guide-bn.md` and `docs/frontend.md` describe the earlier landing (feature index, who-does-what table, animated agent demo) that the 2026-11-16 commits replaced, and `DESIGN.md` is contradicted by the new landing.

### Contract review (`ArcTradeOrders.sol`)

No exploitable defect found in a full read of 783 lines, plus 191 passing tests. Observations, all consistent with the documented design:
- Reentrancy: every state-changing external function is `nonReentrant`; `executeFor` can only be called by the contract itself from `executeMany`, so a failing item is caught without reopening the lock.
- Swap safety: the swap target must be allowlisted (timelocked), approval is exact and reset to zero, and spent input must equal `amountIn` exactly. Output is measured by balance delta and checked against an oracle-derived floor. A router that can move other escrowed tokens through arbitrary calls is the one thing the balance checks do not cover, which is why the allowlist is the key control.
- Owner powers: `pause` and `disableToken` are instant and stop executions (stop-losses will not fire while paused or while a token's feed is disabled), but refunds and cancels always work. Config changes are timelocked and expire after 14 days. The keeper fee can only go down. No renounce, two-step ownership.
- Known limitations: trailing peaks only move when someone calls `pokeTrailing`; an oracle with a 24 h heartbeat can lag the market; keepers choose the route inside the user's slippage; no fee-on-transfer support (checked at deposit).
- Size: 798 bytes below the 24,576 limit. Any new function needs a size check first.
- It is still unaudited. That, not any single bug, is the top risk of the project.

### Backend review

- Gateway, breaker, budgets, timeouts, ranking, fee handling and the token-list filter are sound and well covered by tests. Kyber router and amount are validated before use.
- Operator endpoints are gated by a constant-time bearer check, loopback fallback ignores proxied requests, and error text is redacted.
- Keeper logic (nonces, backoff, batching, provider fallback, profit gate) is careful. Weak spot: it spends most of its RPC budget on the public RPC (finding 4).
- Indexer: idempotent inserts and range halving are correct; Arc has deterministic finality so no reorg handling is acceptable.
- The new `POST /agent-chat` is off by default, limited in size, rate and daily budget, and its output must pass the strict parser. Tested only against a mock endpoint.

## 4. Things that are fine and worth keeping

Exact-amount approvals everywhere; readback plus wallet signature for every agent action; sanitised settings with legacy mapping; `ErrorBoundary`; per-pane mobile layout; honest empty, loading and error states on Trade, Dashboard and Agent; 167 app tests and 191 contract tests; documentation that matches the code in most places.

## 5. The Coolify deployment that never finishes

Evidence I have: the log you pasted stops at "Adding build arguments to Docker Compose build command." (commit `cb6d5df`). Coolify is not on this machine, so I could not see the server, its memory or its Docker log.

What I reproduced here: `docker build --target web` died at step `[build 3/7] COPY --from=deps /app/node_modules ./node_modules` with `failed to solve: Unavailable: error reading from server: EOF`. The Docker engine itself restarted (Docker Desktop containers showed "Up 24 seconds" afterwards, including unrelated projects; they came back on their own). The earlier `bun install` step finished in 44 s for 843 packages. So the heavy step is moving the whole dependency tree into the build stage, not compiling. Also, one base image pull ran at roughly 1 MB/s on this machine.

Likely contributors, most to least supported:
1. **Size of the dependency tree.** 843 packages including six Circle SDKs that only deploy scripts use (finding 12), copied into three stages. On a small VPS this thrashes memory and disk and can sit for a very long time without any error.
2. **Coolify rewrites the Dockerfile.** It added 136 `ARG` lines to four stages. That invalidates the cache on every change and passes every environment variable (including secrets such as `KEEPER_PRIVATE_KEY`) into the build as build arguments.
3. **`# syntax=docker/dockerfile:1.7`** makes BuildKit pull a frontend image from Docker Hub before anything else. Nothing in the Dockerfile needs that version. If the server cannot reach Docker Hub quickly, the build waits silently. Not verified.
4. `docker compose build` builds `api` and `web` in parallel, which doubles peak memory.

To confirm on the Coolify host (run there, nothing here can): `free -h`, `docker stats --no-stream`, `df -h /var/lib/docker`, `docker ps`, `journalctl -u docker -n 50`, `dmesg | grep -i oom`, and `docker buildx du`. If memory is 2 GB or less, cause 1 is almost certain.

Recommended fix, in order: move the Circle SDKs out of `dependencies`; drop the `syntax` line; mark secrets as runtime-only in Coolify so they are not injected as build args; build and push the `web` and `api` images from GitHub Actions and have Coolify pull them, so the server never compiles; and until then give the host swap and build one service at a time.
